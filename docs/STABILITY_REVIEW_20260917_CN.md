# 稳定性与并发检查（2026-09-17）

## 结论与适用范围

已完成本地源码审查、修复和自动化验证，面向单个 Gophish 服务进程、长期组成员增量同步以及千人级临时演练。不能据此宣称服务器已通过千人同时访问或真实邮件吞吐测试。服务器 CPU/内存未提供；用户计划未来迁移 MySQL，当前未提供可测试的 MySQL 实例。

## 本轮已修复

| 问题 | 修复与效果 |
|---|---|
| 队列“先查询、后统一标记”可被并发领取 | 新增 ClaimMailLogs，用事务内条件 UPDATE 领取仍未处理且已到投递时间的行；按 ID 排序降低跨事务锁顺序冲突，仅 RowsAffected=1 的记录交给发送器。 |
| 启动活动与自动同步抢到同一批邮件 | 立即启动只处理创建活动时已占用的原始收件人记录；自动追加的记录由后台领取。 |
| 一个活动配置读取失败导致已领取邮件卡住，并阻断其他活动 | 失败批次释放处理标志；继续处理其他活动，错误保留在日志。 |
| 旧 MailLog 使用 Save，在完成/删除活动后可能重新插入已删除的队列记录 | Lock、Unlock、批量释放、退避改为对已有行 UPDATE；退避超过上限清理对应队列记录；增加完成/删除与旧记录操作回归。 |
| 后台旧状态可能覆盖 Completed | UpdateStatus 对已完成活动不再回写进行中状态；发送每条邮件前检查任务是否仍存在且活动未完成。已进入 SMTP 网络事务的邮件无法追回。 |
| 发送批次无限并发 | 每个 MailWorker 同时最多 8 个批次建立连接/发送，其余等待。每批仍顺序发送，不等于“每秒 8 封”，不涉及外部 SMTP 发信配额。 |
| 空批次、取消连接、重连连接释放等异常路径 | 空批次直接返回；取消返回明确错误，避免 nil sender；重连释放旧连接并关闭最终连接。 |
| 每封邮件获取 SMTP 发件人时加载整个活动、结果和事件 | 复用批次缓存的模板/SMTP 上下文；无缓存时仅获取发信上下文；非法发件人地址返回错误而不空指针崩溃。 |
| 自动同步加载不必要的历史结果列 | 去重查询只读取历史邮箱列，减少内存和传输。 |
| 生成 rid 遇到数据库错误可能无限循环 | 非“未找到记录”的数据库错误立即返回，避免持有事务持续循环。 |
| 用户组更新的部分错误路径未结束事务 | 增加 Begin 检查与 defer Rollback，删除失败立即返回，避免错误路径占用单连接。 |
| 活动列表统计重复扫描 | 所有活动的状态计数合并为一次按活动分组聚合；列表主体加统计共两次查询。保留打开/点击/提交的累计口径及用户归属过滤。 |
| 千人结果页刷新逐行遍历全部结果 | 按 rid 建立索引，匹配由平方级遍历改为线性；1,203 行回归验证匹配次数和重复刷新。 |
| 演练类型标识依赖加载完整活动数据 | summary/results 返回 long_term，升级后前端直接使用轻量响应；旧服务器保留一次兼容读取。普通/长期演练均有只读标识，完成后标注“已结束”。 |

## 已执行的验证

- 8 个并发请求追加同一批 1,200 个不同邮箱：新增总数为 1,200，加上原有 4 人，最终 1,204 条结果。
- 16 个并发领取者使用同一批旧快照领取 1,204 条队列记录：每条仅被成功领取一次。
- SQLite 测试使用内存数据库和产品当前的单连接池；不是实际 MySQL 锁竞争测试。
- 新增人员与完成活动并发，完成后的旧任务 Unlock/Backoff/批量更新不重新生成队列，旧状态不重新打开已完成活动。
- 删除后旧快照不能再领取记录；被延期的任务不能被旧快照提前领取。
- 8 个 worker 并发读取同一批队列不重复入发送器；立即启动不会抢走自动追加的邮件；一个模板缺失的活动不会阻断正常活动。
- 24 个模拟发送批次，最多 8 个同时进入连接阶段，等待批次可继续处理；没有真实 SMTP 或钉钉投递。
- models、worker、mailer、controllers、controllers/api 使用 Go race detector 回归通过；新增数据库错误退出测试与核心变更再次验证。
- JavaScript 普通/长期/已结束标识、名称转义、结果表新增行/重复刷新/状态和展开历史回归；1,203 行结果按线性次数查找；脚本语法检查。
- Go 构建、核心包 go vet 检查；交付包包含 vendor，可离线构建。安装脚本在本机 macOS 隔离目录中使用真实 Go 构建验证通过，原程序备份、配置/数据库/演示文件保留，十个页面文件及迁移均核对一致；未在用户 Linux 服务器执行。

## 仍需处理或验证的生产边界

1. **不能多实例共用发送库。** 启动逻辑 UnlockAllMailLogs 会清除所有处理标志。本轮条件领取减少正常并发争抢，但不构成分布式租约。不要同时启动多个 Gophish 进程使用同一数据库；多实例需单独设计带到期时间和 owner 的领取租约、恢复与领导者机制。
2. **邮件“恰好一次”不能保证。** 邮箱去重保证活动记录不重复加入。若 SMTP 已接收而进程在写入成功状态前退出，重启恢复可能再次尝试投递。本轮不承诺网络故障/断电下绝对不重发。
3. **MySQL 默认仍为单连接。** models.Setup 中 SetMaxOpenConns(1) 同时作用于 SQLite 和 MySQL。未擅自调大连接池。迁移 MySQL 后应在测试库验证隔离级别、锁竞争、事务重试、索引和连接池，再确定参数。
4. **外部服务不响应时的内部资源占用。** 当前有拨号超时，但所带 gomail 未设置覆盖每次 SMTP 读写的超时；远端连接长时间不响应仍可能占住发送槽。本轮按用户要求不评估外部 SMTP 发信额度或限流，读写超时属于后续内部故障恢复工作。此次未修改第三方 SMTP 实现。
5. **持续增长的活动需要归档。** 当前每分钟扫描关联组及活动已参与邮箱，结果页读取全量结果和时间线；累计十万级历史时可能变慢。待实际增长量明确后应增加批量上限、游标/分页、合适索引和归档策略。当前没有“无限人数仍保持每分钟完成”的保证。
6. **同组同时编辑可能覆盖。** 用户组 API 是完整名单保存；多人同时打开同一组再保存可能出现后保存覆盖前保存的意图。建议每组由一个管理员维护，后续可增加版本冲突检测或专用增量成员接口。
7. **钉钉界面不代表发送实现已完成。** 当前源码包含钉钉配置字段与界面，但 SMTP.GetDialer 仍走 SMTP，本轮未找到独立钉钉工作通知发送实现。本轮验证仅限邮件队列，钉钉实际投递不能作为已完成能力承诺。
8. **缺少真实 MySQL/服务器容量验收。** 本地测试不能换算成生产 QPS、每秒发信数或 1,200 人同时点击的容量。需在隔离测试环境对 1,000、2,000、5,000 名单及并行打开/点击进行分级测试，观察响应延迟、数据库锁等待、CPU/内存、错误率与投递队列积压。禁止直接对真实员工做压测。

## 部署与回退

此次包含 Go 后端修改，单独替换网页不会启用并发修复。完整更新包需先停止服务，使用其安装脚本构建、备份原安装目录，再替换程序和列明的页面文件。配置、数据库、演示内容保留。外置 MySQL 需按原运维流程单独备份。本轮不增加数据库迁移。

暂按一个服务进程运行。先用测试组验证：新建普通/长期活动 → 原人员收到一条 → 组里加新人 → 仅新人加入长期活动 → 关闭完成活动 → 不再追加。实际 SMTP 验证由用户在获授权的测试收件人范围进行，本轮未执行。
